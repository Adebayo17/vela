## 1. Purpose

This note describes **how the RTL modules of VELA are verified**: which
references they are compared to, how a Python test drives a Verilog
simulation, what each file of `verif/` does, and how to extend the flow to
a new module.

It applies to the image filters (`grayscale`, `threshold`, `gaussian`,
`sobel`, `median`), to the shared window generator `window3x3`, and to the
OLED display path (`spi_master`, `oled_controller`, see [§6.4](#64-spi-monitor-display-path)).

All tools are open source; **Vivado is not needed** for this verification.

| Tool           | Role                                                |
| :------------- | :-------------------------------------------------- |
| pytest         | test runner, stimulus generation, result comparison |
| NumPy          | golden model and fixed-point models                 |
| Icarus Verilog | `iverilog` compiles, `vvp` simulates the RTL        |
| Verilator      | static lint (`-Wall`)                               |
| GTKWave        | optional waveform viewer                            |

## 2. Three models, two comparisons

The golden model (`python/filters.py`) computes in **floating point**. The
hardware computes in **fixed point** (integers). Their results cannot be
bit-identical, so the verification is split into two independent questions:

```
 python/filters.py         verif/models/filters_hw.py        rtl/<module>.v
 golden model (float) ◄──► fixed-point model (Python) ◄──► RTL (Verilog)
                       ①                                ②
                "close enough?"                   "bit-identical?"
                tolerance per filter              no tolerance
```

| Comparison                          | Question                                                    | Needs a simulator | Pass criterion                     |
| :---------------------------------- | :---------------------------------------------------------- | :---------------- | :--------------------------------- |
| ① fixed-point model vs golden model | Is the fixed-point algorithm faithful?                      | no                | per-filter tolerance (table below) |
| ② RTL vs fixed-point model          | Does the Verilog compute exactly the fixed-point algorithm? | yes               | **exact equality**, every pixel    |

Any difference in ② is an RTL bug. A failure in ① is a design-choice issue
(rounding, saturation, coefficient width), not an RTL bug.

The fixed-point model is written to mirror the RTL arithmetic: same
coefficients, same rounding constant, same saturation, same sorting
network. It is the **specification** of the RTL module.

### Pass criteria per module

| Module      | Fixed-point arithmetic                             | ① vs golden model                                 | ② RTL vs model |
| :---------- | :------------------------------------------------- | :------------------------------------------------ | :------------- |
| `grayscale` | `(77R + 150G + 29B + 128) >> 8`                    | error < 1 LSB                                     | exact          |
| `threshold` | `p > T ? 255 : 0`                                  | exact (`threshold(p/255, T/255)`)                 | exact          |
| `window3x3` | 3x3 window, zero padding                           | exact (`np.pad`, constant 0)                      | exact          |
| `gaussian`  | `(Σ k·w + 8) >> 4`, kernel `[1 2 1; 2 4 2; 1 2 1]` | error ≤ 0.5 LSB                                   | exact          |
| `sobel`     | `min((\|Gx\| + \|Gy\|) >> MAG_SHIFT, 255)`         | exact vs `clip(golden, 0, 255)` (`MAG_SHIFT = 0`) | exact          |
| `median`    | 19 compare-and-swap network (`opt_med9`)           | exact                                             | exact          |

## 3. Directory layout

```
verif/
├── models/            WHAT the hardware must compute            (Python)
│   ├── filters_hw.py      one fixed-point model per filter
│   ├── oled_hw.py         expected SPI traffic of the display (init + pixels)
│   └── pipeline_hw.py     board output: RTL filter chain -> RGB565 (GUI HW view)
│
├── tb/                HOW the module is connected and driven     (Verilog, not synthesizable)
│   ├── tb_grayscale.v
│   ├── tb_threshold.v
│   ├── tb_window3x3.v
│   ├── tb_filter3x3.v     shared by gaussian, sobel, median
│   ├── tb_spi_master.v
│   ├── tb_oled_controller.v
│   └── spi_monitor.v      passive SPI decoder/checker used by the two above
│
└── tests/             THE TESTS                                  (Python, pytest)
    ├── rtl_sim.py         plumbing: .hex files, iverilog, vvp, waveforms
    ├── test_rtl_<module>.py
    ├── test_rtl_lint.py   VELA-NFR-005: Verilator lint + Verilog-2005 check of rtl/
    └── test_pipeline_hw.py  board output model + GUI frame composition (no simulator)
```

| Directory | Contains | Rule |
| :--- | :--- | :--- |
| `python/` | golden model and its tests | knows nothing about the hardware (exception: the GUI's HW view imports `verif/models/pipeline_hw.py`) |
| `rtl/` | **synthesizable** Verilog only | can be added as-is to Vivado |
| `verif/` | fixed-point models, testbenches, co-simulation tests | links the two |
| `tools/` | shared `@requirement` decorator, traceability scanner | shared |

Imports work because `pytest.ini` sets `pythonpath = python verif/models tools`.
They therefore only work **under pytest**. `verif/tests/` deliberately has no
`__init__.py`: pytest would otherwise see two packages named `tests`.

## 4. Execution flow of one test

**Signals are not driven from Python.** Python launches the simulator as an
external program and exchanges data with it **through files only**. The
signals are driven, cycle by cycle, by the Verilog testbench.

Example: `test_matches_model_continuous_stream` in `test_rtl_grayscale.py`.

```
 make rtl-test
  └─ pytest           finds test_*.py / Test* / test_* by name, injects tmp_path
      │
      └─ test_matches_model_continuous_stream(tmp_path)                 [Python]
          ├─ random_rgb(24, 24, seed)       → NumPy image (3, 24, 24)
          ├─ pack_rgb(img)                  → 576 integers 0xRRGGBB
          │
          ├─ run_testbench("tb_grayscale", ["grayscale.v"], pixels, 24, tmp_path)
          │   │                                                         [rtl_sim.py]
          │   ├─ write_hex()                → tmp_path/in.hex
          │   ├─ subprocess: iverilog       compile tb_grayscale.v + grayscale.v
          │   ├─ subprocess: vvp            run the simulation; Python waits
          │   │     ┌───────────────────────────────────────────────────────┐
          │   │     │ Verilog (separate vvp process)                        │
          │   │     │   tb reads in.hex ($readmemh)                         │
          │   │     │   tb drives rst_n, valid_in, r_in, g_in, b_in         │
          │   │     │   grayscale.v responds on each clock edge             │
          │   │     │   tb writes y_out to out.hex on each valid_out        │
          │   │     │   tb prints "DONE" (or "ERROR") and calls $finish     │
          │   │     └───────────────────────────────────────────────────────┘
          │   └─ read_hex()                 ← tmp_path/out.hex
          │
          ├─ grayscale_u8(img)              expected result (fixed-point model)
          └─ assert_array_equal(rtl, expected)   → PASS / FAIL
```

| File | Language | Role | Called by |
| :--- | :--- | :--- | :--- |
| `verif/tests/test_rtl_<module>.py` | Python | builds stimuli, compares results | pytest |
| `verif/tests/rtl_sim.py` | Python | writes `in.hex`, runs iverilog + vvp, reads `out.hex` | the `test_*` functions |
| `verif/tb/tb_<module>.v` | Verilog | **drives the signals** cycle by cycle | `vvp` |
| `rtl/<module>.v` | Verilog | module under test (DUT) | instantiated by the testbench |
| `verif/models/filters_hw.py` | Python | computes the expected result | the `test_*` functions |

**Why this split:** writing the expected result in Verilog would mean
rewriting the model a second time, in a language ill-suited to it. Python
reuses NumPy, the fixed-point models and pytest; Verilog does the one thing
only it can do — run the module cycle by cycle.

## 5. Python ↔ Verilog interface

### 5.1 Channels

| Direction | Channel | Content |
| :--- | :--- | :--- |
| Python → Verilog | file `in.hex` | input pixels |
| Python → Verilog | `vvp` plusargs | file paths, pixel count, gap seed, waveform file |
| Python → Verilog | `iverilog` options | parameter overrides (`-P`), macros (`-D`) |
| Verilog → Python | file `out.hex` | output words |
| Verilog → Python | stdout | `DONE: <n> ...` or `ERROR: ...` |

### 5.2 `.hex` files

Plain text, **one hexadecimal word per line, one line per pixel**, in raster
order (row by row, left to right). Read in Verilog with `$readmemh`, written
with `$fwrite(fd, "%02x\n", ...)`. They live in pytest's temporary directory
and are deleted after the test (see [§8](#8-waveforms) to keep them).

| Module | `in.hex` word | `out.hex` word |
| :--- | :--- | :--- |
| `grayscale` | 24 bits `RRGGBB` | 8 bits |
| `threshold`, `gaussian`, `sobel`, `median` | 8 bits | 8 bits |
| `window3x3` | 8 bits | 72 bits `w00 w01 w02 w10 w11 w12 w20 w21 w22` |

**Packing RGB into 24 bits.** `589f85` is three bytes, R first:

```
   58     9f     85
   R      G      B         0x58 = 5×16 + 8  =  88
                           0x9f = 9×16 + 15 = 159
                           0x85 = 8×16 + 5  = 133
```

| Step | Code | Location |
| :--- | :--- | :--- |
| Python assembles | `(R << 16) \| (G << 8) \| B` | `pack_rgb()`, `test_rtl_grayscale.py` |
| Python writes | `f"{w:06x}"` | `write_hex()`, `rtl_sim.py` |
| Verilog splits | `{r_in, g_in, b_in} <= pixels[sent];` (bits 23-16, 15-8, 7-0) | `tb_grayscale.v` |

**Wide words.** `window3x3` outputs 72-bit words. `read_hex()` returns Python
integers of any width; `run_testbench(..., out_width=72)` splits each word
into 9 bytes, MSB first.

### 5.3 Plusargs (read with `$value$plusargs`)

| Plusarg | Meaning | Required |
| :--- | :--- | :--- |
| `+IN=<file>` | input `.hex` file | yes |
| `+OUT=<file>` | output `.hex` file | yes |
| `+N=<count>` | number of input pixels | yes |
| `+SEED=<int>` | seed for random `valid_in` gaps; `0` = continuous stream | no |
| `+VCD=<file>` | dump all signals to a VCD file | no |

### 5.4 Compile-time options

| Option | Purpose | Python argument |
| :--- | :--- | :--- |
| `-P<tb>.<PARAM>=<v>` | override a **testbench** parameter (e.g. `THRESHOLD`, `IMG_WIDTH`) | `params={"THRESHOLD": 100}` |
| `-D<MACRO>=<v>` | define a preprocessor macro (e.g. `DUT`, `DUT_EXTRA_PARAMS`) | `defines={"DUT": "sobel_filter"}` |

`-P` only reaches the top-level module (the testbench). Module-specific
parameters of the DUT go through `DUT_EXTRA_PARAMS` (see [§6.3](#63-shared-testbench-for-3x3-filters)).

## 6. Testbenches

### 6.1 Common structure

Every testbench follows the same sequence:

1. read plusargs; stop with `ERROR` if one is missing;
2. optionally open a VCD file (`+VCD`);
3. load `in.hex` into a memory (`$readmemh`), open `out.hex`;
4. hold reset for 4 cycles, then release it;
5. **drive** the input pixels (§6.2);
6. **capture** every output for which `valid_out = 1` (an `always @(posedge clk)` block);
7. drain the pipeline with a cycle timeout;
8. check that exactly `N` outputs were captured, print `DONE` or `ERROR`, `$finish`.

The clock is 100 MHz (`always #5 clk = ~clk`). This value has **no effect on
the results** of a functional simulation (see [§13](#13-limitations)).

### 6.2 Driving `valid_in` and the data

`in.hex` contains **data only**. The testbench itself decides, on each cycle,
whether a pixel is presented:

```verilog
while (sent < n) begin
    @(posedge clk);
    if (seed != 0 && ($random(seed) & 3) == 0)
        valid_in <= 1'b0;                     // gap: no pixel this cycle
    else begin
        valid_in <= 1'b1;
        {r_in, g_in, b_in} <= pixels[sent];   // next pixel of in.hex
        sent = sent + 1;
    end
end
```

- Without `+SEED`: `valid_in` stays high, one pixel per cycle.
- With `+SEED`: `valid_in` drops one cycle in four on average, at
  **reproducible** positions (same seed, same gaps). This checks that no pixel
  is lost or duplicated when the stream stalls.

**Modules with `ready_in`** (`window3x3` and the 3x3 filters): a pixel is
consumed only when `valid_in && ready_in` at a rising edge. These testbenches
drive inputs on the **falling edge** and count consumed pixels on the rising
edge, which avoids races with the DUT, and they hold the same pixel until it
is accepted.

### 6.3 Shared testbench for 3x3 filters

`tb_filter3x3.v` serves `gaussian_filter`, `sobel_filter` and `median_filter`,
which share the same interface (`IMG_WIDTH`, `IMG_HEIGHT`, `valid_in`,
`ready_in`, `pixel_in`, `valid_out`, `pixel_out`).

| Macro | Default | Example |
| :--- | :--- | :--- |
| `DUT` | `gaussian_filter` | `-DDUT=median_filter` |
| `DUT_EXTRA_PARAMS` | empty | `-DDUT_EXTRA_PARAMS=",.MAG_SHIFT(3)"` |

### 6.4 SPI monitor (display path)

The display path has no image output: its result is the traffic on the SPI
bus. `verif/tb/spi_monitor.v` watches `sclk` / `mosi` / `dc` **as the SSD1331
would** and:

- rebuilds each byte (MSB first, sampled on the rising edge of `sclk`) and
  writes it as a 48-bit word `0 <dc> <byte> <cycle>`;
- checks **mode 0**: `mosi` never changes while `sclk` is high;
- checks that `dc` is constant during a byte;
- checks every `sclk` half period against `+HALF`, which the Python test
  computes **from the specified frequency** (`CLK_FREQ / SPI_FREQ / 2`), not
  from the RTL formula.

`tb_oled_controller.v` also time-stamps the control signals as
`1 <signal> <value> <cycle>` words (`oled_pmoden`, `oled_vccen`, `oled_res`,
first rise of `s_axis_tready`), so the tests check the power/reset order and
delays. The expected traffic comes from `verif/models/oled_hw.py`.

The real power-up delays (20 ms + 2 × 100 µs + 25 ms + 100 ms ≈ 14.5
million cycles, about one minute) are simulated once, with the RTL default
parameters. This test is marked
`slow` (run by `make test-all` and `make rtl-test`, skipped by `make test`);
the other tests override the four delay parameters with short values.

Extra `run_testbench()` arguments used here: `plusargs` (e.g. `+HALF`,
`+NBYTES`, `+MAXCYC`), `tb_sources` (verification files such as the monitor),
`raw=True` (output words as Python integers), `timeout`.

## 7. Test design

### 7.1 Two classes per module

Each `test_rtl_<module>.py` holds two classes matching the two comparisons
of [§2](#2-three-models-two-comparisons):

| Class | Comparison | Simulator |
| :--- | :--- | :--- |
| `Test<Module>Hw` | ① fixed-point model vs golden model | no |
| `Test<Module>Rtl` | ② RTL vs fixed-point model | yes (skipped if iverilog is missing) |

### 7.2 Stimulus categories

| Category | Purpose | Examples |
| :--- | :--- | :--- |
| Random images | general coverage | every module, fixed seeds |
| Exhaustive inputs | prove a small input space completely | 256 pixel values (`threshold`), 256 gray levels (`grayscale`), 9! orderings (median network) |
| Extreme values | overflow, saturation | white image (`gaussian`), maximum-gradient window = 1530 (`sobel`) |
| Structured patterns | expose a specific mistake | impulse → kernel weights (`gaussian`); ramp `pixel = index + 1` → any off-by-one shift (`window3x3`) |
| Several image sizes | parameterization, borders | 8x6, 5x3, 24x24, 32x32 |
| Consecutive frames | state reset between frames, end-of-frame flush | 2 or 3 frames back to back |
| `valid_in` gaps | handshake | `seed != 0` |
| Many ties | comparator correctness | salt-and-pepper noise, 3-level image (`median`) |

### 7.3 Counting tests

The total reported by pytest counts **executions**, not functions:
`@pytest.mark.parametrize` runs one function once per value. For example,
`test_exhaustive_all_pixels` runs for 6 thresholds and counts as 6 tests.

| File | `test_*` functions | Tests |
| :--- | ---: | ---: |
| `test_rtl_grayscale.py` | 5 | 5 |
| `test_rtl_threshold.py` | 5 | 15 |
| `test_rtl_window3x3.py` | 6 | 9 |
| `test_rtl_gaussian.py` | 7 | 10 |
| `test_rtl_sobel.py` | 10 | 18 |
| `test_rtl_median.py` | 8 | 11 |
| `test_rtl_spi_master.py` | 5 | 7 |
| `test_rtl_oled_controller.py` | 7 | 7 |
| `test_rtl_lint.py` | 2 | 16 (2 checks × 8 files) |
| **Total RTL** | **55** | **98** |

List them without running: `pytest --collect-only verif/tests/test_rtl_threshold.py`.

## 8. Waveforms

```bash
make rtl-waves K=grayscale          # K = pytest -k filter (module or test name)
gtkwave build/waves/test_rtl_grayscale__test_matches_model_with_valid_gaps/wave.gtkw
```

With `VELA_WAVES=1` (set by `make rtl-waves`), each test writes a directory
`build/waves/<file>__<test>/`:

| File | Content |
| :--- | :--- |
| `wave.vcd` | every signal of the simulation (testbench and DUT) |
| `wave.gtkw` | GTKWave view preloading clock, reset, inputs, outputs (buses in hex) |
| `in.hex`, `out.hex` | copies of the exchanged files |

Without `VELA_WAVES`, nothing is recorded and test runs keep their speed.
DUT internals remain available in GTKWave's tree under `dut`. The `.gtkw`
file stores the absolute path of the VCD, because GTKWave resolves it from
the current directory. `build/` is git-ignored and removed by `make clean`.

## 9. Mutation checks

A passing test only proves something if it **can fail**. A mutation check
injects a deliberate bug into the RTL, runs the tests, and expects failures;
the RTL is then restored. Mutations are manual checks, not part of the test
suite.

| Module | Real bugs injected | Detected | Equivalent mutants |
| :--- | :--- | :--- | :--- |
| `threshold` | `>` → `>=` | 1/1 | — |
| `window3x3` | border masking (top, left, right), first output one step early, `ready_in` stuck at 1, `c_row` not reset | 6/6 | 3 |
| `gaussian` | edge weight ×1, center ×2, rounding removed, 11-bit adder, output bits shifted | 5/5 | — |
| `sobel` | absolute value removed, Gy weight ×1, saturation removed, 11-bit gradient, `MAG_SHIFT` ignored | 5/5 | — |
| `median` | last CAS removed, CAS reversed, wrong output, `valid` stage skipped | 4/4 | 1 |
| `spi_master` | MOSI changed on the rising edge, half period too short, `start` accepted while busy, byte truncated | 4/4 | — |
| `oled_controller` | init byte changed, pixels sent as commands, high/low bytes swapped, `tready` not lowered, reset too short, `tready` raised during init; VCCEN raised at power-up, 25 ms or 100 ms wait skipped, Display ON missing | 10/10 | — |
| lint test (NFR-005) | SystemVerilog cast `8'(...)` in `threshold.v` | 1/1 | — |

An **equivalent mutant** changes the code but not the behavior, so no test
can detect it. They were analyzed one by one:

- `window3x3`: zero injection during the flush (the values are masked anyway),
  explicit reset of `c_col` (it wraps to 0 by itself), explicit reset of `ptr`
  (a circular buffer works from any start address);
- `median`: `>` → `>=` in a compare-and-swap (swapping equal values changes nothing).

## 10. Requirement traceability

Each test is tagged with the requirement it covers:

```python
from vela_testing import requirement

@requirement("VELA-FR-008")
def test_matches_model_continuous_stream(self, tmp_path):
    ...
```

`make trace` scans the tests and the requirements file and writes
`docs/requirement/traceability_report.md` (git-ignored, regenerated on demand).

| Requirement | Covered by |
| :--- | :--- |
| VELA-FR-008 (RTL bit-exact vs fixed-point model, close to golden model) | filter and `window3x3` tests |
| VELA-FR-009 (OLED display: init + RGB565 pixels over SPI mode 0) | `test_rtl_spi_master.py`, `test_rtl_oled_controller.py` |
| VELA-NFR-001 (100 MHz clock) | SCLK frequency and real-delay tests at 100 MHz; `make synth` constraint |
| VELA-NFR-003 (throughput) | planned: cycle-count test in simulation |
| VELA-NFR-005 (Verilog-2001, lint-clean) | `test_rtl_lint.py` (also `make rtl-lint`) |
| VELA-NFR-002, VELA-NFR-004 (timing, resources) | `make synth` + `tools/synth_summary.py` (not a pytest test) |

## 11. Adding a new RTL module

1. **Fixed-point model** — add `<module>_u8()` (or equivalent) to
   `verif/models/filters_hw.py`, mirroring the intended RTL arithmetic.
2. **Comparison ①** — in `verif/tests/test_rtl_<module>.py`, class
   `Test<Module>Hw`: compare the model with the golden model and justify the
   tolerance (rounding, saturation).
3. **RTL** — write `rtl/<module>.v`: Verilog-2001 only, header comment
   naming its reference model, `make rtl-lint` clean, `iverilog -g2005` clean.
4. **Testbench** — reuse `tb_filter3x3.v` if the interface matches; otherwise
   copy the closest testbench and keep the plusarg conventions of [§5.3](#53-plusargs-read-with-valueplusargs).
5. **Comparison ②** — class `Test<Module>Rtl`, decorated with
   `@requires_iverilog`, calling `run_testbench()`. Cover the categories of
   [§7.2](#72-stimulus-categories) that apply.
6. **Traceability** — tag every test with `@requirement(...)`.
7. **Mutation check** — inject a few realistic bugs and confirm the tests fail.
8. **Waveforms** — no extra work: `make rtl-waves K=<module>`.

## 13. Limitations

- **Functional simulation only.** The simulation checks the values computed,
  not propagation delays: results are identical at any clock frequency.
  Timing (VELA-NFR-002) is verified by synthesis and place-and-route.
- **Simulator semantics.** Icarus Verilog may accept constructs that synthesis
  treats differently (e.g. incomplete sensitivity lists, multiple drivers).
  Lint (Verilator) and synthesis remain necessary.
- **No downstream back-pressure.** The filters have no `ready_out`; the
  testbenches always accept outputs. Integration with `oled_controller`
  (which has `tready`) is a Phase 3 concern.
- **Single-channel filters.** The 3x3 filters process one 8-bit channel; the
  golden model `gaussian()` / `median()` also accept RGB.
- **Manual mutation checks.** They are not automated; they were run when each
  module was written.
- **Display protocol only.** The display tests check what is sent on the
  bus (bytes, order, timing), not whether the SSD1331 interprets the init
  commands as intended: the expected sequence mirrors the RTL ROM.
  Datasheet conformance (e.g. power sequencing) is a review item.
